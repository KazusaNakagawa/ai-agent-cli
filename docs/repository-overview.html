    My World Briefing — リポジトリ解説

    地政学イベント・株価変動・セクターテーマを毎朝収集し、特定のポートフォリオに引きつけて解釈したうえで、 3 分で読めるブリーフィングを Discord と Notion に配信する LLM エージェントシステム。 本ドキュメントは、このリポジトリの構造・設計判断・運用方法を一望するための解説資料です。

    この資料の位置づけ

    正本は README.md（日本語版 README.ja.md）と docs/ 配下の各ドキュメントです。 本資料はそれらを読む前の全体像として、リポジトリを初めて触る人が「どこに何があり、なぜそうなっているか」を掴めることを目的にしています。 個別の手順は各ガイドへのリンクを辿ってください。

    コンセプト

    一般のニュース・市況サービスは、不特定多数に向けて同じ紙面を配ります。このエージェントは読者が 1 人しかいない前提で、 拾ったイベントを自分の保有銘柄・ウォッチテーマ・地政学リスクに紐づけ、 「これが自分にとって何を意味するか」まで踏み込んだ文章を毎日生成します。 情報を集めるツールではなく、自分のレンズを通して情報を解釈するエージェントという位置づけです。

    技術的な難所は LLM を呼ぶこと自体ではありません。非決定的なエージェントを、毎朝無人で走らせて信頼できる水準まで持っていくことです。 部分障害のハンドリング、実行漏れからの復旧、昨日のモデル出力が今日のプロンプトになる構造でのインジェクション封じ込め、コストの可視化 — 以下に示す設計の大半は、この制約から導かれています。

    全体アーキテクチャ

    入口（CLI スクリプト / Web UI）、ドメインごとのハンドラ、共通基盤、外部サービスという 4 層構成です。 非対話の生成系の LLM 呼び出しは claude_runner.py という 1 点を通ります。

    外部サービスのうち Claude Code CLI だけが claude_runner を経由します。yfinance・Discord・Notion へは 各ハンドラの fetcher/ notifier/ が直接アクセスするため、図では線を省略しています。 データフローの作図元は docs/architecture.drawio、シーケンスレベルの詳細は docs/sequence-diagrams.md にあります。

    日次ブリーフィングの流れ

    bin/run.sh の 1 回の実行で起きることを、時系列に並べたものです。

    1. 市況データの収集
      fetcher/stocks.py が yfinance から保有銘柄・ウォッチ銘柄の前日比を取得します。 対象は config/briefing.json の定義に従います。
    2. プロンプト構築と並列生成
      generator/briefing.py がセクション別のプロンプトを組み立て、run_claude() を並列に呼び出します。 リアルタイム検索は Claude Code CLI 内蔵の WebSearch が担当し、外部ニュース API は使いません。
    3. ローカル書き出し（配信より先）
      notifier/local_md.py が output/briefing_YYYY-MM-DD.md を書き出します。 ネットワーク配信より先にディスクへ落とすのは、Discord や Notion が落ちても生成物を失わないためです。 あわせて output/charts/ にポートフォリオ比較チャートの PNG が出力されます。 チャート生成は best_effort のステップで、yfinance の不調で落ちてもブリーフィング本体の配信は止まりません。
    4. Discord / Notion への配信
      それぞれ独立した notifier として実装されており、片方の失敗がもう片方を巻き込みません。 Discord へはテキスト配信のあとにチャート PNG を続けて送ります（添付のアップロード失敗も配信済みのブリーフィングを巻き込みません）。
    5. 使用量とコストの記録
      usage_logger.py が実行ごとのトークン使用量を残し、Web UI の Monitor タブで日次・モデル別に可視化されます。

    金曜日はこれに加えて weekly_handler.py が走り、週次リキャップと Notion コメントの取り込みを行います。

    主要な設計判断

    判断理由
    外部ニュース API を使わない リアルタイム検索は Claude Code CLI 内蔵の WebSearch が担う。API キー管理と契約が 1 つ減る
    Anthropic API のトークン従量課金を使わない Claude Code CLI の OAuth セッション上で動作する。有効な Claude 有料プラン（Pro/Max）が前提で、無料プランでは動かせない
    生成系の LLM 呼び出しの入口を 1 か所に集約 非対話の claude 実行が src/claude_runner.py を通るため、認証モード・環境変数の扱い・リトライの実装が 1 つしか存在しない（対話セッションは別経路）
    地政学 → 株価の因果を毎日の出力に織り込む 「ニュースの要約」ではなく「自分のポジションへの影響」を出力するための、プロンプト設計上の固定要件
    個人データはリポジトリに入れない 実データは .example とスキーマだけを追跡し、実体は Git 管理外に置く（後述）

    生成系 LLM 呼び出しの単一入口

    claude_runner.run_claude() が非対話の claude CLI 呼び出しを引き受けます。 ブリーフィング生成・週次リキャップ・評価パイプラインなど、出力をキャプチャして扱う経路がこれに当たります。 認証まわりはモード依存で、state.read_state().auth_mode（既定は cli）に応じて _build_env() が subprocess の環境変数を組み立てます。

    auth_modeANTHROPIC_API_KEY の扱い結果
    cli 既定環境変数から除去するclaude CLI が自身の OAuth セッションを使う
    apiKeychain →.env の順で解決し注入するAPI キーによる従量課金で動作する

    実装時の注意

    claude への新しい subprocess 呼び出しを追加するときは、必ず _build_env(state.read_state().auth_mode) を経由させてください。 このヘルパーの外側で ANTHROPIC_API_KEY を直接セットすると、認証モードの切り替えが壊れます。

    例外 — 対話セッションは別経路

    bin/chat.sh の対話 Q&A だけは claude_runner を通りません。 src/chat_cli.py が同名の run_claude() を持ち、subprocess.run() を直接呼びます。 利用者がその場で入力する以上、子プロセスに端末をそのまま渡す必要があり、 出力をキャプチャして再試行する前提の claude_runner には載せられないためです。

    このため、対話セッションには claude_runner のリトライ・使用量ログが効きません。 認証も claude_env() が ANTHROPIC_API_KEY を常に除去するため、 auth_mode の設定に関わらず cli モード相当で固定されます。 claude を呼ぶコードを追加・監査するときは、この 1 か所が単一入口の外にあることを前提にしてください。

    無人運用のための設計

    このシステムは、LLM のステップが失敗する・ハングする・使い物にならない出力を返すことを前提にしており、 かつ朝 5 時には誰も見ていないことを前提にしています。

    懸念対処箇所
    部分障害 — セクター調査が落ちてもブリーフィング本体は届けたい src/handler.py のデグレードモード。notifier/local_md.py がネットワーク配信より先にディスクへ書き出す
    部分的な取りこぼし — DarkWake で長いセクター調査だけが切れた bin/recover.sh → src/recovery_handler.py。セクター調査のみを再実行して当日の MD と Notion ページに追記する。当日分にセクター失敗の注記がなければ no-op（claude 呼び出しゼロ）で、実行前に src.power.is_system_awake() がマシンの覚醒を確認する
    プロンプトインジェクション src/prompt_safety.py。neutralize_user_text が設定文字列中のロールマーカーを無害化し、wrap_untrusted が再利用される LLM 出力（昨日のブリーフィングを今日のチャットに投入するケース）を「命令ではなくデータ」として囲む
    一時的な API / ネットワークエラー src/transient_errors.py。claude_runner 内でリトライ
    コストの逸脱 src/usage_logger.py / usage_monitor.py / claude_rates.py。Web UI の Monitor タブで可視化。公表レートのないモデルはゼロ円として混ぜず、合計から除外する

    前提条件 — スリープ中の Mac はスケジューラでは救えない

    上記はすべて、スケジュール時刻にマシンが本当に起きていることを前提としています。すなわち 蓋を開けた状態で AC アダプタに接続していること（AC 接続時は pmset -g custom が sleep 0 を返す）。 蓋を閉じれば電源の種類に関係なくスリープします。

    蓋を閉じたバッテリー駆動の Mac では、5 時のジョブは約 45 秒しかない DarkWake の中で起動します。 claude CLI の接続が API Error: Connection closed mid-response で切れ、その後の一時エラーリトライが ブリーフィングを 1 つも生成しないままサブスクリプションの利用枠を食い潰します （2026-08-12 の実測で API 換算 $2 超相当、Issue #443）。 caffeinate -ims でも防げません — -s は AC 電源時のみ有効で、バッテリー駆動の DarkWake を呼び出し完了まで延命できないためです。

    このため、メンテナの環境では launchd や cron ではなく手動実行を現行の運用としています。 詳細と実測ログは docs/guides/launchd-setup.md と docs/guides/cron-setup.md にあります。

    セットアップと実行

    前提: Python 3.11〜3.13（すべて CI で実行）、uv、認証済みの Claude Code CLI、Discord Bot、Notion インテグレーション。

    git clone https://github.com/KazusaNakagawa/ai-agent-cli.git
cd ai-agent-cli
cp .env.example .env      # DISCORD_TOKEN, NOTION_API_KEY などを設定

cd apps/python
uv venv .venv
uv pip sync requirements.txt

cd ../web && npm install  # Web UI を使う場合のみ

    スキーマを変更するとき

    .example と tests/config/briefing.json の両方を同時に更新してください。片方だけ直すと CI が実態とずれます。

    テストと CI

    cd apps/python && .venv/bin/pytest -v   # Python 側の全スイート
cd apps/web && npm test                 # vitest（ユニット + コンポーネント）
cd apps/web && npm run test:e2e         # Playwright

    両スイートとも push 時に GitHub Actions で実行されます（.github/workflows/pytest.yml、web.yml）。 テストは apps/python/tests/config/briefing.json を読み込み、conftest.py が src.config の import より前に BRIEFING_CONFIG_PATH を固定するため、実行に個人設定は一切不要です。

    依存関係は requirements.in のみを編集し、uv pip compile --universal --python-version 3.11 で requirements.txt を再生成します。サポート範囲が 3.11〜3.13 のため、単一インタプリタで解決したロックでは 古い CI レグが必要とする backports が落ちます。

    開発規約

    ブランチとコミット

    dev が作業ブランチです。フィーチャーブランチは dev から分岐し、PR の base も dev。 main は dev → main の PR でのみ同期します。

    • ブランチ名: feature/ fix/ refactor/ docs/ chore/
    • コミット: Conventional Commits（<type>: <英語の要約>）
    • PR: タイトルはコミット形式に準拠（70 文字未満）、本文は箇条書きサマリ + テスト計画のチェックリスト

    コードスタイル

    • コード内のコメント・docstring は 英語で統一（Python / TypeScript とも）。ユーザー向けのチャット応答は日本語だが、コード内ドキュメントは英語のみ。1 ファイル内で言語を混ぜない
    • README.md と README.ja.md は翻訳ペア。同一コミットで両方を更新し、見出し数とテーブル行数が一致することを確認する
    • apps/web の画面を変更したときは、コードリーディングだけで済ませず Playwright で実ブラウザ検証する。まず問題を再現し、修正で消えることを確認する
