# アイデアメモ: 家計・資産管理機能（Money）

## 概要

銀行・カード・証券の明細を取り込んで、**月次の収支**と**払い続けている固定費（サブスク・保険）**を可視化する。
既存の `src/portfolio_snapshot`（投資資産のストック）に対して、こちらは**キャッシュフロー（フロー）**を担当し、最終的に「純資産＝現金＋投資」で合流させる。

想定ユーザーは本リポジトリのメンテナ本人のみ。マルチユーザー・SaaS 化は想定しない。

## 解決したい課題

1. 毎月いくら出て行っているのか、口座をまたぐと分からない
2. サブスク・保険など「気づかず払い続けているもの」の年額が把握できていない
3. 投資（`holdings.json`）と現金が別管理で、純資産と生活防衛資金の厚みが一目で分からない

---

## 実データからの発見（設計の前提）

2口座・13ヶ月分の明細（163行）を実際に読み込んで確認した事実。以下はすべて設計判断の根拠になる。
※ 金額・口座名義などの個人データは本ドキュメントには記載しない（`input/` は gitignore 済み）。

### 1. 残高列は「取り込みの正しさを機械的に検算できる唯一の手段」

両行とも各明細に取引後残高を持つ。`前行の残高 − 出金 ＋ 入金 == 当行の残高` を全行でチェックすると、
行の抜け・重複・転記ミスがゼロ件であることを証明できる（実際に両ソースで不整合 0 件を確認済み）。

→ **残高チェーン検算をインポータの必須ステップにする。** 画像からの手起こしや、期間を分けてダウンロードした
CSV の結合でも、これがあれば「取り込めたが実は1行抜けている」を検出できる。

### 2. 口座間振替を除外しないと月次収支は使い物にならない

証券口座への資金移動と定期預金系商品への振替が混じった月は、**月次収支の符号が反転する**（実データで2ヶ月該当）。
振替は「支出」ではないのに支出として計上されるため。

振替の検出は2系統が必要:

| 手段 | 効き方 | 実データでの結果 |
|---|---|---|
| **クロス口座ペアリング**（同額・逆符号・日付差 ≤2日で自動突合） | 自分の口座間の振込を高精度で検出 | 対象13件中11件が自動成立 |
| **摘要ルール**（証券会社名・自分名義・定期預金商品名） | ペアの片側しか明細に無いケースを拾う | 残り2件はこちらでしか拾えない |

ペアリングが失敗した2件の理由も明確だった: (a) 片方の口座の CSV 期間外、(b) 取り込み対象外の口座への振込。
→ **ペアリングは「必ず成功する前提」で組んではいけない。** 未成立分は「振替候補」として人間に提示し、
判断結果をルールに書き戻す設計にする。

### 3. 支出分析の解像度は、銀行明細だけでは頭打ちになる

実データでは、**全明細163行のうち67行（41%）が単一の摘要**（キャッシュレス決済へのチャージ）に集中していた。
銀行から見えるのは「チャージ額」だけで、何に使ったかは一切分からない。
同様に、カード会社への引き落としも銀行明細では1行に潰れる。

→ 銀行明細だけで得られるのは **「固定費の把握」と「月次の収支と貯蓄率」** まで。
カテゴリ別の変動費内訳が欲しければ、カード明細・決済アプリ明細の取り込みが別途必要。

13ヶ月分の支出構成:

| 区分 | 構成比（概算） | 銀行明細だけで分かること |
|---|---|---|
| 保険（口座振替） | 約4割 | 相手も金額も分かる |
| **カード引き落とし（当初「収納代行」と誤認）** | 約1/4 | 金額のみ。**中身はカード明細にしかない** |
| 決済アプリへのチャージ | 約1/4 | 金額のみ |
| その他・ATM | 1割未満 | 金額のみ |

**当初この分類を誤り、「カード明細を入れても最大の不透明項目は解けない」と結論していた。これは誤りだった。**
毎月変動する最大の支出を「複数サービスの一括請求（収納代行）」と解釈していたが、
実際にはカード明細を入手して照合した結果、**そのカード自体の引き落とし**であることが判明した。
根拠は発見7（銀行摘要の略称がカード発行会社名と一致し、引き落とし日・金額レンジも整合）。

→ **決定: カード明細は取り込む（決定1）。** カード明細こそが、支出の約1/4を占める
最大の不透明ブロックの内訳そのものである。実際、1ヶ月分の明細だけでも
複数のサブスクリプション課金が個別行として現れており、課題2（払い続けているものの把握）に直結する。

カード明細を入れると、銀行側の引き落とし1行とカード明細の個別行が**二重計上**になる。
ただしこれは `引き落とし額 == 当該請求月の明細合計` という厳密な等式で検算できるため、
残高チェーン（発見1）と同じ算術的な保証のもとで相殺できる。**この検算を必須にする**（FR-3.5）。

決済アプリへのチャージは、明細が入手できるまでは**その時点の支出として計上**する。
現金は実際に口座から出ているのでキャッシュフローとしては正しく、失われるのは内訳だけ。

### 4. 定期支出は「固定額」ではなく「毎月同じ相手に払う」で捉えるべき

実データの定期支出候補（月数3以上で再出現する摘要）は9件見つかったが、**そのうち金額が完全固定なのは1件もなかった**。
保険料ですら年1回だけ増額される月があり、収納代行系は毎月3倍近く変動する。

→ **「同額が毎月」で検出するとほぼ全て取りこぼす。** 検出条件は
「正規化後の摘要が3ヶ月以上・別々の月に出現」とし、金額は中央値とレンジで提示する。

### 5. 摘要文字列の正規化は必須（日本の銀行特有）

実データに含まれていた表記ゆれ:

| 現象 | 例 | 対処 |
|---|---|---|
| CP932 / CRLF | 楽天銀行 CSV | デコードを parser 側で吸収 |
| 全角英数 | `ＤＦ．ＧＰ` | NFKC |
| 濁点の分離（U+309B が独立文字） | `セ゛ンホレン` | U+309B → U+3099（結合文字）に置換してから NFKC |
| 全角ハイフンが長音として使われる | `マ－ケテインク` | カタカナ直後の `-` を `ー` に戻す |
| 小書きカナが使われない | `ッ` `ャ` が大書きで届く（`キヤノン` 式） | 照合キーでは小書き→大書きに畳む |
| 全角スペース区切り | `振込ＩＢ２　氏名` | 空白正規化 |

→ **表示用の正規化文字列**と、**ルール照合用のマッチキー**（さらに畳んだもの）を分けて持つ。
ルールを人間が書くとき、銀行の表記ではなく世間で通っている表記をそのまま書けるようにするため。

### 6. 画像しか出せない口座がある

三菱UFJ銀行は明細のテキスト/CSV 出力ができず、スクリーンショットからの手起こしになった。
→ **手入力（人間が編集できる CSV）を一級市民として扱う。** 「CSV 取り込みのおまけ」ではなく、
正規のインポート経路の一つとして parser を用意する。残高チェーン検算（発見1）がこの経路の品質保証になる。

### 7. 文字コードが壊れたまま保存されたファイルは、静かに取り込まれてはいけない

入手したカード明細は、CP932 のファイルを UTF-8 として読んだ状態（不正バイトが U+FFFD に置換された状態）で
保存されており、**店名の約9割が復元不能な形で失われていた**。金額・日付・合計は無傷なので、
取り込み自体は「成功」してしまう。しかし店名が消えているため、分類も定期支出検出も一切効かない。

→ **入力に U+FFFD が含まれていたら取り込みを拒否する**（FR-1.7）。
「取り込めたのに使えない」を防げるのは、この検査だけである。残高チェーン検算（発見1）も
金額しか見ないためこの破損を検出できない。

副次的な発見として、**この破損は決定論的**である。CP932 の2バイト文字のうち、
下位バイトが ASCII 範囲のものはそのまま生き残る。したがって
「候補文字列を CP932 でエンコードし UTF-8 で `errors="replace"` デコードした結果」と突き合わせれば、
破損した文字列を**照合により同定できる**。実際にこの方法でカード名を完全一致で特定し、
発見3 の誤りを訂正できた。ただし全店名を候補列挙で当てるのは非現実的なので、
復元機能は作らず、**再取得を促すエラーメッセージ**に留める。

### 8. カード明細は銀行明細と「検算の質」も「中身の性質」も違う

健全なカード明細を1ヶ月分入手して構造を確認した結果:

| 観測 | parser への要求 |
|---|---|
| ファイル末尾に合計行があり、**明細合計・支払総額列・合計行の3つが完全に一致した** | 残高列が無くてもこの一致を検算に使える（FR-1.8 が成立することを実証） |
| **利用日がソートされていない**（月末の行が月内の行より前に来る） | 取り込み時に並べ替える。順序に依存する検算（残高チェーン）は原理的に使えない |
| ヘッダ行と明細行で**列数が違う**（ヘッダは口座情報、明細は取引） | ヘッダを「列名の行」として扱わない。列数不一致を異常としない |
| 合計行は先頭列が空 | 明細行と区別して読み飛ばす |
| 外貨建て取引は備考欄に**通貨・適用レート・約定日**が入る | 円換算額と原通貨額の両方を保持できる。為替による月次変動の説明に使える |

**中身の性質についての重要な訂正**: 「固定費は銀行明細で把握でき、カードに乗るのは変動費」という
当初の整理は誤りだった。実際のカード明細には**公共料金（電気・ガス・水道）と通信費が含まれていた**。
つまり固定費の相当部分がカードの内側にある。

→ **定期支出の検出（FR-4.3）は、銀行明細よりカード明細でこそ効く。**
発見4 の「同額ではなく同じ相手で捉える」方針は、公共料金のように毎月必ず変動する項目に
そのまま当てはまる。逆に言えば、カード明細を入れないと固定費一覧は不完全なままになる。

なお1ヶ月分では定期判定（3ヶ月以上の再出現）が成立しないため、**過去分の取得が前提**になる。

### 9. 相殺は実データで完全に成立した（FR-3.5 の実証）

8請求月分のカード明細を取り込み、各請求月の明細合計と、銀行側の該当引き落とし額を突き合わせた。
照合可能だった**7請求月すべてが一円単位で一致**した（残る1件は銀行明細の取得期間外で照合不能）。

→ FR-3.5 の相殺は推定ではなく**算術的に保証された処理**として実装できる。
併せて、当該引き落としがこのカードのものであることも確定した（発見3の訂正の裏付け）。
8ファイルすべてで自己検算（明細合計＝合計行）も一致しており、FR-1.8 も成立している。

### 10. 定期支出の検出は「出現月数」だけでは誤る

8請求月分で発見4の条件（3ヶ月以上・別々の月に出現）を実際に適用したところ、
**都度購入の EC 決済が定期支出として混入した**。毎月必ず買い物をしていれば毎月出現するため、
出現頻度では固定費と区別できない。

**変動係数（標準偏差 ÷ 平均）を併用すると実データできれいに分離した**:

| 変動係数 | 実データでの中身 | 扱い |
|---|---|---|
| 〜0.35 | サブスク、通信、公共料金、定額サービス | 定期支出として確定扱い |
| 0.35〜0.8 | チャージ系、金額の振れる継続課金 | 定期支出候補として提示（要確認） |
| 0.8〜 | EC の都度購入 | 定期支出から除外 |

発見4の「同額で判定すると全滅する」は正しいが、**下限だけでなく上限も要る**という修正になる。

**変動係数は明細行ごとではなく、請求月ごとの合計に対して計算する。**
行単位で計算すると、同じ相手に**定額サブスクと従量課金が混在**している場合に破綻する。
実データでは、あるサブスクが1ヶ月だけ従量課金を伴っていたために行単位の変動係数が閾値をわずかに超え、
**7ヶ月連続で払い続けている定額サービスが固定費一覧から丸ごと脱落した**。
月合計に切り替えると同じ相手が正しく固定費として検出される。
同じ理由で、月に複数回課金される相手（アプリ内課金など）も月合計で見ないと誤判定する。

同じ検証で、正規化・検出について3つの追加要件が出た:

1. **摘要に含まれる期間表記を落とさないと同一相手がばらける** — 「N月分」が付く公共料金は、
   除去しないと毎月別々の相手として扱われ、定期支出として一度も検出されない。
   実データでは除去によりユニーク店名が2割ほど減り、検出数が増えた
2. **同一サービスでも加盟店名が途中で変わる** — あるサブスクが途中で別表記に変わり、
   連続した課金が2つの相手に分裂した。文字列処理では統合できないので、
   **別名を1つにまとめるエイリアスルール**が要る（FR-2.5）
3. **請求周期は毎月とは限らない** — 隔月請求のものがあり、出現月数を月数で割って年額換算すると誤る。
   周期（毎月／隔月／年1回）を出現間隔から推定してから年額換算する

### 11. 自分の名前で振替を判定すると、自分が払った支出が消える

Phase 1 を実装して実データを流した時点で見つかった不具合。
振込の摘要には受取人だけでなく**依頼人名（＝自分）**が入る。自分名義の振込を口座間移動とみなす
ルール（FR-3.3）を摘要全体に当てると、**自分が振り込んだ支出がすべて振替と誤判定される**。
実データでは家賃の支払いが支出から消えていた。金額が大きいうえ、レポート上は
「振替として除外」としか出ないため、見ていないと気づけない。

→ 自分名義の判定は、摘要の**依頼人名より前（＝相手方を指す部分）に限定する**。
自分の口座への本当の送金は受取人としても自分の名前が出るので、この制限をかけても検出できる。

一般化すると、**摘要は「相手を表す部分」と「取引の付帯情報」が混在した1つの文字列**であり、
ルールを全文に当てると付帯情報に引っかかる。付帯情報を落としてから照合する。

## 機能要件

### FR-1 インポート
- FR-1.1 銀行ごとの CSV を取り込む。文字コード・列構成の差は parser が吸収する
- FR-1.2 人間が手編集できる共通 CSV フォーマットからも取り込める（画像しか出せない口座向け）
- FR-1.3 ヘッダ行の内容からどの parser を使うかを自動判定する（ユーザーに口座を選ばせない）
- FR-1.4 取り込みは冪等。同じファイルを何度入れても明細は増えない
- FR-1.5 残高列がある場合、残高チェーンを検算し、不整合があれば取り込みを中止して該当行を示す
- FR-1.6 取り込み結果（新規N件・重複M件・期間）をサマリー表示する
- FR-1.7 入力に U+FFFD（文字化けの痕跡）が含まれていたら取り込みを拒否し、再取得を促す（発見7）
- FR-1.8 カード明細を取り込む（決定1）。残高列を持たないため、代わりに
  **ファイル内の合計行と明細合計の一致**を検算に使う（実データで成立を確認済み ← 発見8）。
  利用日は未ソートで届くため取り込み時に並べ替える
- FR-1.9 口座ごとに明細のカバー期間を記録する。カード明細が無い期間は、銀行側の引き落とし行を
  支出として計上する（FR-3.5 と対になる）

### FR-2 正規化・分類
- FR-2.1 摘要を正規化し、表示用文字列と照合用マッチキーを両方保持する
- FR-2.2 ルール（正規表現→カテゴリ）で分類する。ルールは設定ファイルで追加できる
- FR-2.3 どのルールにも当たらなかった明細は `uncategorized` として一覧できる
- FR-2.4 (Phase 5) 未分類分のみ LLM に投げ、確定した対応をルールに書き戻す
- FR-2.5 マッチキー生成時に摘要の**期間表記（「N月分」「YYYY年M月」等）を除去**する（発見10）
- FR-2.6 別表記を1つの相手に束ねる**エイリアスルール**を設定ファイルで定義できる（発見10）

### FR-3 振替判定
- FR-3.1 口座間の振替を収支から除外する
- FR-3.2 クロス口座ペアリング（同額・逆符号・日付差 ≤2日）で自動検出する
- FR-3.3 摘要ルールでも振替を指定できる。自分名義による判定は摘要の**依頼人名より前**に限定する（発見11）
- FR-3.4 ペアが成立しなかった振替候補を「要確認」として提示する
- FR-3.5 カード会社への引き落としは、当該請求月のカード明細が取り込まれている場合のみ振替として除外する。
  除外する条件は `引き落とし額 == 当該請求月の明細合計` の**一致を検算できたときに限る**（決定1 / 発見3）。
  一致しない、または明細が無い場合は引き落とし行を支出として計上し、「要確認」に出す
- FR-3.5b 決済アプリへのチャージは、明細を入手できるまで振替にせず支出として計上する
- FR-3.6 証券口座への入金の扱いは**設定で切り替えられる**ようにする（決定2 / FR-4.7）

### FR-4 レポート
- FR-4.1 月次収支（収入・支出・収支・貯蓄率）を出力する。振替は除外する
- FR-4.2 カテゴリ別の内訳を出力する
- FR-4.3 定期支出を、月額中央値・レンジ・直近支払日・年額換算つきで一覧する。判定条件は
  **3ヶ月以上・別々の月に出現し、かつ変動係数が閾値以下**（発見10）。閾値超えは候補として別枠に出す。
  変動係数は明細行ごとではなく**請求月ごとの合計**に対して計算する（発見10）
- FR-4.3b 年額換算は請求周期（毎月／隔月／年1回）を出現間隔から推定してから計算する（発見10）
- FR-4.3c **出現が途中で止まった相手を「停止したサービス」として検出する**。
  解約済みの棚卸しと、意図しない停止（決済失敗など）の両方に効く
- FR-4.3d ルールに書いた注記（`note`）を定期支出一覧にそのまま表示する。
  明細からは中身が分からない相手（保険など）に「未確認」を貼り、調べ直しの重複を防ぐ
- FR-4.4 生活防衛資金カバー月数（現金残高 ÷ 平均月支出）を出力する
- FR-4.5 前月比・前年同月比で大きく動いたカテゴリだけを差分として示す
- FR-4.6 (Phase 6) `holdings.json` と合流させ、純資産（現金＋投資）を出す
- FR-4.7 **証券口座への入金を2通りに解釈したレポートを両方生成し、並べて比較できるようにする（決定2）**
  - パターン A（振替）: 証券入金は資産の置き場所を変えただけ。支出に含めない
  - パターン B（投資支出）: 証券入金は「投資」カテゴリの支出。含める
  - 収支・貯蓄率・平均月支出・生活防衛資金カバー月数の**すべてが両パターンで変わる**ため、
    差が出る指標を1つの表に A/B 併記する
  - 比較して片方に決めた後は、設定 `securities_deposit_treatment: "transfer" | "expense"` で
    既定を固定し、レポートは単一パターンに戻せるようにする

### FR-5 出力
- FR-5.1 月次レポートを Markdown で `output/money/` に書き出す
- FR-5.2 出力はローカルファイルのみ（決定3）。Discord / Notion への配信は行わない

## 非機能要件

- NFR-1 完全ローカル。銀行 API・アカウントアグリゲーションサービスには接続しない（認証情報を持たない）
- NFR-2 明細データ・設定は git 管理下に置かない（`input/` `output/` は gitignore 済み）
- NFR-3 LLM 呼び出しは Phase 5 まで発生させない。Phase 5 以降も未分類分のみ・ルール昇格でゼロに漸近させる
- NFR-4 LLM を呼ぶ場合は既存の `src/claude_runner.run_claude()` 経由（CLAUDE.md の単一入口ルール）
- NFR-5 Python 3.11–3.13 で動作。新規の外部依存を追加しない（標準ライブラリの `csv` / `unicodedata` で足りる）

## スコープ外

| 項目 | 理由 |
|---|---|
| 銀行 API / スクレイピングによる自動取得 | 認証情報を持たない方針（NFR-1）。CSV は手で落とす |
| 保険の重複保障チェック | 明細から分かるのは保険料だけ。判断には約款が要る |
| 予算超過のリアルタイム通知 | 明細取り込みが手動である以上、リアルタイム性が成立しない |
| 家族・複数ユーザー | 本人専用（既存の briefing / portfolio と同じ前提） |
| 税務・確定申告向けの帳票 | 要求が別物。必要になったらエクスポートで対応 |
| Discord / Notion への配信 | 出力はローカルのみ（決定3）。既存 `notifier/` は使わない |
| 日次ブリーフィングへの支出ペース挿入 | 同上。ブリーフィングは配信を伴うため対象外にする |
| 決済アプリ明細の取り込み | 生データが未入手。入手できればカードと同じ仕組みで扱える（FR-3.5b） |
| 文字化けしたファイルの自動復元 | 候補照合で1件ずつなら同定できるが全店名の当てはめは非現実的。再取得を促す（発見7） |

## データモデル

### 明細（transaction）

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | str | 重複排除キー。`account`＋`date`＋`amount`＋`desc_key`＋`balance` のハッシュ |
| `date` | str (ISO) | 取引日 |
| `account` | str | `rakuten_bank` / `mufg` / … |
| `amount` | int | 円。**入金 +／出金 −** の符号付き1列に正規化する |
| `balance` | int \| None | 取引後残高。チェーン検算に使う |
| `desc_raw` | str | 元の摘要（無加工で保持。ルールを直すとき原文が要る） |
| `desc` | str | 正規化後の表示用摘要 |
| `desc_key` | str | 照合用マッチキー（小書きカナ・長音を畳んだもの） |
| `category` | str | ルールで付与。未分類は `uncategorized` |
| `is_transfer` | bool | 振替なら true（収支計算から除外） |
| `transfer_peer` | str \| None | ペアリングで対になった明細の `id` |
| `source_file` | str | どのファイル由来か（取り込み直しの追跡用） |

**符号を1列に正規化する理由**: 楽天銀行は符号付き1列、UFJ は出金/入金の2列。
下流のすべての計算が符号1列を前提にできるよう、差異は parser の中だけに閉じ込める。

### ストレージ

`output/money/transactions.jsonl`（1行1明細、追記型）。

**SQLite ではなく JSONL を選ぶ理由**: 既存の永続化（`journal_store` / `job_store` / briefing 出力）がすべて
ファイルベースで、SQLite は本リポジトリに1箇所も存在しない。個人の家計は年2〜3千行の規模で、
全件ロードしても体感ゼロ。テキストなので壊れたとき人間が直せるし、差分もそのまま読める。
将来レスポンスが問題になったら SQLite に移す（スキーマは既に固定されているので移行は機械的）。

### 取り込みフロー

```
input/money/*.csv
  → parser 自動判定（ヘッダ行の内容で選ぶ）
  → 行を Transaction に変換（符号1列に正規化）
  → 文字化け検査（U+FFFD があれば中止し再取得を促す）
  → 検算  ── 銀行: 残高チェーン / カード: 合計行と明細合計の一致。不整合があればここで中止
  → 摘要正規化（desc / desc_key）
  → id を計算して既存ストアと突合（重複はスキップ）
  → ルール分類 + 振替ルール適用
  → 全口座を通してクロス口座ペアリング
  → カード引き落としの相殺（引き落とし額 == 当該請求月の明細合計 を検算できた場合のみ）
  → JSONL に追記 + 取り込みサマリー表示
```

ペアリングと相殺を最後に置くのは、相手側の口座が**後から**取り込まれることがあるため。
毎回の取り込み後にストア全体へ再適用する（明細数が小さいので全走査でよい）。
これにより「先に銀行だけ取り込んで支出計上 → 後からカード明細を入れると自動で内訳に置き換わる」が成立する。

### CLI 案

```bash

```

## 考慮事項

- **個人データの取り扱い**: 明細・設定・レポートはすべて gitignore 配下に置く。
  設計ドキュメントやテストフィクスチャに実際の金額・名義を書かない（本ドキュメントも同様）。
- **テストフィクスチャ**: 実明細は使えないので、実データで観測した**構造**（濁点分離・全角・2列/1列・
  振替ペア・残高チェーン）だけを再現した合成 CSV を `tests/money/fixtures/` に置く。
- **手起こし CSV の信頼性**: 画像からの転記は残高チェーン検算に完全に依存する。
  残高列が読めない画像しか無い口座は、取り込み対象外とする判断も必要。
- **カバー期間の食い違い**: 口座ごとに取得できる明細期間が違うと、振替ペアリングが端で必ず失敗する。
  レポートには「全口座が揃っている期間」を明示し、その外は参考値として扱う。
- **チャージと利用のズレ**: 決済アプリはチャージ日と利用日が一致しない。チャージ時点で支出計上するため、
  月内に使い切らなかった残高の分だけ月次がぶれる。年単位ではならされるので許容するが、
  「月次は現金の出入り、内訳は不明」という前提をレポートに明記する。
- **二重計上**: 相殺（FR-3.5）を外すとカード分の支出が丸ごと2倍になる。
  実データで「相殺後の支出合計 == 相殺前の銀行のみ集計」が成り立つことをテストで固定する。
- **カードの締め日と利用日のズレ**: カード明細の利用日と引き落とし日は1〜2ヶ月ずれる。
  月次収支は現金主義（引き落とし月）で集計し、カード明細は**内訳の説明**にのみ使う。
  「7月の支出の内訳」に6月の利用が並ぶので、レポートに請求月と利用月の対応を明記する。
- **カテゴリ分類の主戦場はカード明細側になる**: 銀行明細は相手が数十種類しかないが、
  カード明細は店名が毎月増える。`uncategorized` が最も溜まるのはここなので、
  ルール運用の負荷はカード明細の行数に比例すると見ておく。
- **`uncategorized` の放置**: ルール方式は運用しないと腐る。`review` サブコマンドで未分類を必ず可視化し、
  未分類が一定割合を超えたらレポート冒頭で警告する。

## 決定事項

| # | 論点 | 決定 | 設計への影響 |
|---|---|---|---|
| 1 | カード・決済アプリの明細を含めるか | **カード明細は含める / 決済アプリは未入手のため保留** | 当初「含めない」としたが、根拠にしていた「最大の不透明項目はカード明細でも解けない」が**誤りだった**（そのブロックはカード自身の引き落としだった ← 発見3・発見7）。カード parser と相殺（FR-3.5）・カバー期間管理（FR-1.9）が必要になる |
| 2 | 証券口座への入金の扱い | **2パターン生成して比較のうえ判断** | レポートが A/B 併記になる（FR-4.7）。収支・貯蓄率・平均月支出・カバー月数の4指標が両方の値を持つ。判断後に設定で単一に固定できるようにしておく |
| 3 | レポートの配信先 | **ローカルのみ** | `notifier/` を使わない。Discord/Notion 配信と日次ブリーフィングへの挿入はスコープ外に移動（旧 FR-5.2/5.3 を削除） |

決定2 の比較は、実データが揃った時点で1度だけ行う判断であり、恒久機能ではない。
比較して結論が出たら `securities_deposit_treatment` を固定し、`--compare-securities` は残しつつ既定から外す。

## 実装フェーズ

| Phase | 内容 | 対応する要件 |
|---|---|---|
| 1 ✅ | 銀行 parser 2本 + 文字化け検査 + 正規化 + 重複排除 + 残高検算 + 振替判定 + 月次収支 CLI | FR-1.1–1.7, FR-2.1–2.3, FR-3.1–3.4, FR-3.5b, FR-4.1, FR-4.2, FR-5 |
| 2 | カード parser + 合計行検算 + カバー期間管理 + 引き落とし相殺 | FR-1.8, FR-1.9, FR-3.5 |
| 3 | 証券入金 A/B 比較レポート → 方式を決定して設定に固定 | FR-3.6, FR-4.7 |
| 4 | 定期支出の検出、カバー月数、前月比・前年同月比 | FR-4.3–4.5 |
| 5 | 未分類のみ LLM 分類 → ルール書き戻し | FR-2.4 |
| 6 | `holdings.json` と合流して純資産 | FR-4.6 |
| 7 | Web UI（Money タブ）: 手入力フォーム・グラフ | — |

**Phase 1 と 2 を分ける理由**: Phase 1 は銀行2口座だけで完結し、Phase 2 の相殺はカード明細に依存する。
分けておくと、カード明細のカバー期間（現時点で8請求月）を超える過去については Phase 1 の計上のまま扱え、
明細が増えた分だけ自動で内訳に置き換わる。データは既に揃っているので、続けて着手して構わない。

**Phase 3 を早い位置に置く理由**: 決定2は「比較して判断する」ものなので、判断材料を早く出す必要がある。
一方この判断は貯蓄率の定義を変え、Phase 4 の平均月支出・カバー月数の分母に直結するため、Phase 4 より前に置く。

**Phase 5（LLM）を後回しにする理由**: 振替判定が無いと月次収支は壊れるが、LLM 分類が無くても
固定費の把握と収支は成立する。ルールで当たらない分だけを後から埋めればよい。

**Phase 7 を最後にする理由**: スキーマが固まる前に UI を作ると作り直しになる。
Phase 1–4 を CLI で数ヶ月回してから着手する。

## 次に必要なもの

**Phase 1–2 に必要なデータは揃っている**（銀行2口座 + カード8請求月）。以下は精度を上げるための追加分。

- カード明細の**さらに過去分**（現在8請求月）。銀行明細と同じ期間まで遡れると、
  定期支出の検出と前年同月比が全期間で効く
- 決済アプリの利用明細（入手できれば FR-3.5b をカードと同じ相殺方式に格上げできる。
  ここが残る最後の「金額しか分からない」ブロック）
- 証券口座の入出金明細（Phase 3 の A/B 比較の精度が上がる。無くても比較自体は成立する）
